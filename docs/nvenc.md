# NVENC

[Rubylight docs](README.md) › [Reference](README.md#reference) · [Architecture](architecture.md) · [Hardware matrix](hardware-matrix.md)

Rubylight encodes with AMF on an AMD GPU and with NVENC on an NVIDIA GPU. With `encoder = auto`, the host picks the encoder from the vendor of the GPU that captures. NVENC is called through NVIDIA's driver ABI (`rust/windows/graphics/src/nvenc.rs`), API 11 to 13, on the compute conversion's D3D12 device or the capture's D3D11 device. Its settings are the `nvenc_*` keys ([configuration](configuration.md)). Intel and software encoding stay removed; those PCs use [Rubylight 2.6.x](https://github.com/RamazanKara/Rubylight/releases/tag/v2.6.0).

## Parity with AMF

Each row lists a feature the AMF path has and how NVENC provides it. Fake-driver tests in `rust/windows/graphics/src/nvenc/tests.rs` cover every NVENC row except the GPU scheduling row, whose tests are in `gpu_priority.rs`.

## D3D12 conversion

With `gpu_compute_conversion` on (the default), NVENC takes the compute queue's output as AMF does. The session opens on the compute queue's `ID3D12Device` (`Session::open` with an output fence):

- **The GPU waits, not the CPU.** For the D3D12 interface `nvEncMapInputResource` "does not provide synchronization guarantee" (`nvEncodeAPI.h`). Each picture's input is an `NV_ENC_INPUT_RESOURCE_D3D12` whose `inputFencePoint` waits for the conversion's fence at its value.
- **Output goes to READBACK buffers.** Each conversion target gets a buffer of twice an uncompressed picture (at most 16 MiB), registered as `NV_ENC_OUTPUT_BITSTREAM` and passed as an `NV_ENC_OUTPUT_RESOURCE_D3D12`. Its `outputFencePoint` signals the session's own fence.
- **Completion is read from the output fence.** The poll locks a frame once that fence reaches the frame's value and never waits on the CPU. With `nvenc_output_event` (on by default) the fence also wakes the stream thread as the oldest frame is written, instead of on the next 100 µs output poll, which stays as the bound. A frame the fence never reaches fails at the completion timeout.
- **What the D3D12 interface leaves out.** It has no weighted prediction, so `nvenc_weighted_prediction` warns and stays off. Slice delivery returns whole frames there; set `gpu_compute_conversion = false` for either.
- **Driver floor.** The D3D12 interface needs API 12.0, NVIDIA driver 522.25 or newer. An older driver, a missing D3D12 device or a refused session warns (`encoder_conversion`) and converts on the D3D11 graphics queue, as AMF falls back. 8-bit native 4:4:4 (`AYUV`) uses the D3D12 compute conversion (through an `R8G8B8A8_UINT` UAV, since `DXGI_FORMAT_AYUV` is invalid as a UAV view format) and supports encoder focus, falling back to the D3D11 graphics queue if a driver or GPU refuses it. 10-bit native 4:4:4 (`YUV444_10BIT`) stays on the D3D11 graphics queue with CUDA, because NVENC's D3D12 interface refuses `YUV444_10BIT`, so encoder focus is off for it. A D3D12 session that falls back at creation keeps the graphics queue for the rest of the stream; a running D3D12 path that fails twice within a minute demotes stickily too, so a broken path cannot stall twice every five-minute retry.

## Encoder focus

Focus works as on AMF: the D3D12 compute conversion builds the importance map from its still-age detector (`compute::Converter::latest_map`), and the same rules pick the frames that carry it ([`amf::focus`](../rust/windows/graphics/src/amf/focus.rs)). No map goes on a keyframe, a recovery picture, the encoder's first frame or the 30 frames after them, or when the map is uniform or not newer than the last one used. Without the D3D12 conversion, focus is off with the same reason as on AMF.

- **Delta map.** NVENC takes the map as a per-picture `qpDeltaMap` (`NV_ENC_QP_MAP_DELTA`): one signed offset per 16x16 macroblock for H.264, per 32x32 CTB for HEVC (the only CTB size NVENC codes) and per 64x64 superblock for AV1 (`nvenc::focus_deltas`). Turning focus on switches `qpMapMode` with a reconfigure, without a reset or a keyframe. The emphasis map is H.264-only, so it is not used.
- **Same weight as AMF.** Each importance step is half a QP (two q-index steps on AV1), the effect AMF's map measured on the RX 7900 XT. The offsets are centred on the picture's mean importance, so the map moves bits between blocks and leaves the frame's QP to the rate control and its one-frame VBV.
- **Startup check.** The probe encodes half-and-half maps, as on AMF, on a session of its own with the delta map and per-block statistics, so the codec check never depends on either. GeForce drivers cap the sessions open at once, so the probe closes the stream's session first and opens it again after, never two at a time. It reads each block's QP from `NV_ENC_OUTPUT_STATS_BLOCK` and needs an effect of 2 QP (8 q-index on AV1). Block statistics need API 12.1, NVIDIA driver 531.61 or newer (`NV_ENC_CAPS_OUTPUT_BLOCK_STATS`); without them focus reports that ROI cannot be verified.
- **Verification during a stream.** `encoder_focus_verify` turns block statistics on when the encoder is made, and `qp_delta` then reports the QP difference between the least and most important blocks, as on AMF.

The D3D11 conversion builds no map, so focus needs the D3D12 conversion on NVENC too.

## Driver settings and Reflex

Beside the encoder, a host that streams with an NVIDIA GPU serves the NVIDIA driver's global 3D settings in the graphics settings panel (Nightjar's stream menu, the console's game page and the native API's [`/radeon` endpoints](native-api.md#radeon-state-and-writes)), read and written through NVAPI (`rust/windows/graphics/src/nvidia_settings.rs`): Low Latency Mode, Max frame rate, Vertical sync, Power management mode, Texture filtering quality, Anisotropic filtering and Smooth Motion (driver 571.86 or newer). As with Radeon settings, the host journals the PC's own values before it changes them and puts them back when the session ends, after a crash too; a combination the panel cannot put back exactly reads as `custom` and is left alone. RTSS's limit mode offers NVIDIA Reflex, and a host that streams with an NVIDIA GPU uses it on its own for virtual-display streams and frame-generation games (`framegen::Policy::for_gpu`).

## RTX HDR and RTX Video enhancement

Once the NVIDIA components are installed (**All settings → Picture → Integrations → NVIDIA components**, which downloads Rubylight's NGX adapter and NVIDIA's RTX Video SDK 1.1.0 runtime from this version's release), Rubylight runs two of NVIDIA's RTX Video SDK 1.1.0 features on the captured picture before conversion and encoding ([configuration](configuration.md#rtx-hdr-and-rtx-video-enhancement)):

- **RTX HDR** (NGX TrueHDR) turns an SDR capture into an FP16 scRGB picture for an HDR stream. The streamed display stays in SDR while it runs. Its contrast, saturation, middle gray and peak brightness follow the game's NVIDIA driver profile where one sets them.
- **RTX Video enhancement** runs NGX VSR with the output at the input's size, so it removes compression artefacts and sharpens without scaling. Strength 1 to 25, 26 to 50, 51 to 75 and 76 to 100 map to VSR quality levels 1 to 4; 0 turns it off. It takes 8-bit SDR and FP16 HDR captures and leaves a 10-bit PQ capture as it is. VSR's model is SDR, so an FP16 picture goes through an SDR proxy normalized around 203-nit white (`rust/windows/abi/src/shaders/rtx_video.hlsl`), and a resolve pass adds back only the change the model made.

NGX is called from `butterpollo_truehdr.dll` (`rust/truehdr-runtime`), an MSVC adapter the GNU host loads at run time by full path from the component's folder (`%ProgramData%\Butterpollo\nvidia` for the installed host), after checking it against the SHA-256 recorded at install and NVIDIA's DLLs against the digests in `rust/core/src/nvidia_component.rs` (`rust/host/src/nvidia_component.rs` downloads and installs them). It is the only code that links NVIDIA's NGX library, built against its static C runtime so that the adapter needs no Visual C++ Redistributable, and it gives NGX a data folder of its own and its own folder for NVIDIA's DLLs. The host (`rust/host/src/nvidia_enhance.rs`, `rust/windows/graphics/src/{truehdr,rtx_video}.rs`) checks both features on the streaming GPU after the install and at each start, in a process of its own (`butterpollo.exe --nvidia-probe`, given 30 s): a crash or hang inside NGX there turns both off with the reason on the console's app page and leaves a crash report in the profile, and the host starts either way. It reports them in serverinfo's `NvidiaEnhancements` bitmask; the console and Nightjar show their controls only where a bit is set. When D3D12 compute conversion and D3D11.4 shared fences are available, both filters output into shared NT-handle pool textures (`SHARED_NTHANDLE | SHARED`, with RTX Video HDR resolving directly into a pooled render-target texture) signalled by a shared D3D11→D3D12 fence so downstream conversion and NVENC can stay on D3D12; otherwise they fall back to a non-shared D3D11 pool on the graphics queue. A failure turns the enhancement off for the session with a visible warning; it never switches encoders.

The per-app settings, the one pre-encode slot that RTX HDR takes first, and the HDR proxy follow Foundation Sunshine's image enhancement (its per-application design and its DLSS NR HDR filter).

**DLSS denoising is not offered.** Earlier ideas used NVIDIA's DLSS ray-reconstruction denoiser (DLSS NR) as a pre-encode clean-up. NGX gives DLSS features only to applications NVIDIA has registered by application ID, and Rubylight neither presents another application's ID nor patches around that check. DLSS NR proper therefore needs NVIDIA's NGX support for third-party applications; RTX Video enhancement uses the RTX Video SDK, which NVIDIA licenses for redistribution in any application.

## Assumed NVIDIA defaults

Rubylight has not measured these defaults on NVIDIA hardware. They follow NVIDIA's Video Codec SDK 13.0 game-streaming guidance and the Sunshine forks, in this order: ULL tuning, CBR, quarter-resolution two-pass, a one-frame VBV, infinite GOP and spatial AQ on. P1 is the fastest preset. `auto` split keeps the driver's implicit mode and forces split only when one engine's estimate misses the frame budget; `driver_decides` keeps only the implicit mode; the **Lowest latency** stream preset asks NVENC to split at every preset.

These choices are assumptions, not NVIDIA measurements:

- Forcing split in the Lowest latency preset and in `auto`'s budget case can show a seam at low bitrate; `nvenc_split_encode = disabled` or `driver_decides` avoids it.
- The budget trigger uses Foundation Sunshine's per-preset calibration. NVIDIA's application note suggests P2 to P7 may be slower than that calibration, so a high preset can still miss the frame interval, especially where split cannot engage; the guard then lowers it to P1 and reports `over_at_floor`.
- The D3D12 session, its fences and its READBACK output have not run on NVIDIA hardware. Failures demote to the D3D11 graphics queue, now stickily for NVENC.
- Spatial AQ and quarter-res two-pass are kept in every preset because NVIDIA recommends them for CBR and low-latency streaming; their NVIDIA encode-time cost is not measured here.

## Checking NVIDIA code

No NVIDIA GPU runs our tests, so NVIDIA code is checked against the vendor's headers and samples and never reported as run on hardware. Check every foreign declaration's parameters and the order of calls, as author and again in review, and give the reviewer the headers' path: NVENC's are vendored (`rust/THIRD_PARTY.md`); the RTX Video SDK is `rtx-video-sdk-1.1.0` in the dependencies folder after `rust\build.ps1 -Nvidia`. NVAPI has no headers here; a report says which calls rest on other hosts' code alone.

## Not run on NVIDIA hardware

The rows above pass the fake-driver tests. These behaviours follow NVIDIA's headers and other hosts' code and have not yet run on an NVIDIA GPU:

- Subframe completion: `hwEncodeStatus` 2 as the end of a picture, and the slice offsets a partial lock reports. The debug lines of the first four frames settle both.
- Keyframes within the one-frame VBV, which the driver does not guarantee.
- Rate control changes applied with frames in flight.
- The stall policy's waits during game loading.
- The D3D12 session: fence points, READBACK output and completion by fence.
- Encoder focus: the delta map's effect per codec, `qpMapMode` switched by a reconfigure, and the block statistics the probe reads.
- The GPU clocks profile: that the driver takes it for the running host, and NVENC's encode time with it on and off on a lightly loaded GPU.
- The driver settings: reading and writing each one through NVAPI, and the restore after a session and after a crash.
- Native 4:4:4: the D3D12 compute AYUV path (`yuv444_ayuv_cs`, `yuv444_ayuv_menu_cs`, `yuv444_ayuv_focus_cs`), D3D11 AYUV and stacked-plane 10-bit inputs (`yuv444_planes_cs` / `yuv444_planes_menu_cs` writing an `R16_UINT` UAV with `yuv444_planes` / `menu_yuv444_planes` pixel-shader fallback), the High 4:4:4 and FREXT sessions (including H.264 4:4:4 on D3D12 and older cards or drivers), and the startup check's 4:4:4 encodes. The ignored tests `native_444_keeps_a_one_pixel_chroma_checkerboard` and `native_nvenc_loss_recovery_and_444_hdr_decode` (cases `h264-444`, `hevc-444`, `hevc-444-hdr`) decode the output with FFmpeg and check the chroma at full resolution.
- Async D3D11/CUDA output events: registering manual-reset Win32 events via `nvEncRegisterAsyncEvent`, resetting them before `nvEncEncodePicture`, and waking the stream thread via `Encoder::output_event()`.
- Non-blocking bitstream locks and coalesced rate control: unconditional `doNotWait = 1` on `nvEncLockBitstream` (including synchronous non-subframe sessions), skipping the trailing immediate `collect()` when only the freshly submitted frame is pending, setting `vbvInitialDelay = vbvBufferSize` on `nvEncInitializeEncoder` and every `nvEncReconfigureEncoder`, and coalescing bitrate and frame-cap VBV changes into a single `nvEncReconfigureEncoder` call.
- CUDA 10-bit 4:4:4 async interop (paired with `yuv444_planes_cs` / `yuv444_planes_menu_cs` `R16_UINT` UAV and pixel-shader fallback): registering the D3D11 stacked-plane texture with `CU_GRAPHICS_REGISTER_FLAGS_READ_ONLY`, binding a `CU_STREAM_NON_BLOCKING` stream via `nvEncSetIOCudaStreams` (passing `CUstream*` after `nvEncInitializeEncoder`), running `cuGraphicsMapResources` / `cuMemcpy2DAsync_v2` / `cuGraphicsUnmapResources` on that stream without nested context pushes, and skipping redundant CUDA copies on scene-cut re-encodes and static repeat-frame cache hits.
- NVENC pre-drain RFI fast paths and static repeat-frame conversion caching on D3D12 and D3D11 sessions (and dynamic HDR buffer headroom via `frame_pool::copy_with_headroom`).
- RTX HDR and RTX Video compute-queue continuity: `GpuPool::shared()` / `GpuPool::shared_rtv()` outputs with `D3d11Signal` shared fences, GPU-ordered `GpuImage::order_d3d11()` in place of CPU `ready.wait()`, direct FP16 RTV resolve in `rtx_video::HdrPasses`, cached VSR SRV/RTV views, and the cached `ID3D11Multithread` lock in `rust/truehdr-runtime`.
